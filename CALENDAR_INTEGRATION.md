# Google Calendar: local implementation, not sandbox-connected

## API / UI seam
- Private solo owner only. No workspace/team selector, membership permission or shared calendar data. No caller-supplied owner ID; current verified cookie user is authoritative and expectedActorId pins the tab.
- GET /api/workspace/calendar (initial authenticated actor bootstrap), then ?expectedActorId=<current UUID> on subsequent reads => {actorId, available, connection}. available means valid server configuration, **not provider connectivity**. connection is null or {status,calendar:"primary",generation,syncedAt,windowStart,windowEnd,fresh,retryAt,lastError,revocationPending}. Status: connecting / connected / reconnect / disconnected. A successful token exchange means authorized; only fresh=true means recently synchronized. Never relabel a mock response as a real connection.
- POST same-origin JSON, maximum 2048 characters, closed fields: {action:"connect",expectedActorId,calendar:"primary",consent:true} => {actorId,authorizationUrl}; {action:"sync",expectedActorId} => {actorId,synced:true}; {action:"disconnect",expectedActorId} => {actorId,disconnected:true,revocationPending}. No query parameters on mutations. Connect explicitly consents only to the primary calendar's busy periods. Redirect the browser only to returned Google authorization URL.
- GET /api/workspace/calendar/callback validates exact configured HTTPS origin and authenticated original user, atomically consumes hashed state, decrypts PKCE verifier, exchanges code, rechecks current user and stores encrypted tokens with generation CAS. Success 303 to /workspace/connections?calendar=authorized. Denial/error leaves a fail-closed attempt: disconnect before starting again. Error responses contain no provider body, code, token or SQL detail.
- 401 sign-in, 403 origin, 400 malformed/consent, 409 changed/work in progress/callback failure, 413 oversized, 415 non-JSON, 503 unavailable. Responses private no-store and no-referrer.

## SQL booking seam — no parent patch needed
Additive 20261118090000_workspace_calendar.sql creates BEFORE INSERT OR UPDATE trigger calendar_booking_guard on existing workspace_scheduling_bookings. Confirmed rows check **blocked_start / blocked_end**, including local buffers, with half-open overlap. Missing/disconnected connection preserves local-only behavior. Connecting/connected/reconnect with missing, failed, older-than-five-minute or uncovered snapshot blocks confirmation (P0001, handled by existing scheduling route). Cancellation remains possible. The trigger, snapshot replacement, first-connect and disconnect take the same owner-specific advisory transaction lock, plus connection row lock. No old migration or booking RPC edited.

Browser roles have no SELECT or writes to credential/state/mirror tables. All three have forced RLS and no policies. Authenticated calendar_status(uuid) returns only current owner's sanitized metadata after auth.uid equality. calendar_service(text,uuid,jsonb) is service_role-only, fixed search_path; this trusted server boundary accepts actor only from verified auth, never client ownership. Intended Supabase function ownership/grants need separate deployment inspection.

## Custody and lifecycle
- Random 256-bit state stored SHA256, random PKCE verifier encrypted; ten-minute expiry, one pending attempt per owner, atomic delete-on-consume; account/origin/generation bound. S256, fixed callback, offline consent. Only https://www.googleapis.com/auth/calendar.freebusy requested; broad returned scopes rejected. No profile/email/calendar picker scopes.
- AES-256-GCM with fresh 96-bit nonce, authenticated owner + purpose AAD, version + key ID envelope. Separate server-provisioned keyring, no hardcoded production key or fallback to OAuth/Supabase secret. Old decrypt keys retained during rotation; newly written tokens use active key. Key loss requires reconnect, never plaintext recovery.
- Durable 90-second lease and token-version/generation CAS serialize refresh + snapshot. Refresh-start marker persists before provider call. If process dies after potential rotation, expired refresh lease transitions to reconnect and discards old token rather than blindly refreshing. Every late token/snapshot write after disconnect or another lease is denied. Rotation saved before busy query. Errors invalidate freshness and persist bounded retry time; 429 Retry-After (seconds/date) respected within the supported 24-hour window; longer waits transition to reconnect/manual review rather than retrying early. Successful sync minimum interval 30 seconds. No automatic retry loop.
- Disconnect atomically increments generation, deletes state/busy/token custody, clears leases. **Provider revocation is pending, not claimed completed.** No revoke network call or token-retaining revocation queue. User must remove application access in Google account; current pending flag intentionally cannot be cleared locally without provider proof. In-flight authorization may have created a remote grant even if local CAS rejects; callback tells user revocation may be needed. Reconnect requires explicit disconnect then new consent; the old pending-revocation warning is retained.

## Bounded provider implementation
Direct server fetch to fixed Google token and freeBusy endpoints, no redirects, no-store, 15-second timeout. Primary only; full now-to-31-days freebusy snapshot, maximum 2000 intervals, one-MiB streaming response-body guard. Validates response window, primary result and calendar errors before atomic replacement. Stores only UTC interval instants; titles, attendees, event bodies and calendar lists never ingested. Google resolves recurrence/all-day/timezones into instants. Empty successful busy array is valid; incomplete/error/overflow response never clears mirror or becomes fresh.

This is **not incremental events sync**: no events.list, syncToken/410, pagination, webhooks/watch renewal, event mapping or calendar writes. No attendees, invites or sends. Existing external-calendar changes can occur after a fresh snapshot: five-minute freshness is not a cross-provider reservation or double-booking guarantee. No scheduler is installed; explicit sync action refreshes. Beyond 31 days or stale view fails closed until synchronized/explicitly disconnected.
