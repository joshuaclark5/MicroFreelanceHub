## Verified facts
- Private `workspace_scheduling_mutate`, public submit and public slot-window functions already share `pg_advisory_xact_lock(hashtextextended(owner_id::text,73118))`.
- The prototype creates a time-off interval under that same lock and adds an insertion guard to the actual restored bookings table. Both existing private and public submission functions reject new overlaps.
- A five-day range is inclusive in one explicitly chosen business timezone and represented as a half-open UTC interval. Appointment **buffers** are included in conflict checks; exact non-overlapping endpoints remain allowed.
- Existing confirmed appointments remain confirmed. Retrying an already-confirmed private booking operation returns the prior record rather than creating another appointment or failing because time off was added later.
- Separate PostgreSQL connections proved both lock orderings, with `pg_blocking_pids` confirming actual waiting: time off first rejects the waiting booking; booking first is preserved and counted when time off is created.
- Reference boundary tests cover New York spring/fall days and five-day ranges, Havana's repeated midnight, Sao Paulo's midnight gap, Lord Howe half-hour shifts, Troll two-hour shifts, Kathmandu's quarter-hour offset and Apia's skipped civil day. An empty skipped-day range is rejected. Anonymous prototype creation is rejected.

## Public-preview gap closed in the local prototype
Both `public_booking_service` preview mode and `public_booking_window` now omit prototype time-off overlaps, including appointment buffers. The patch is limited to the disposable clone; neither deployed function nor an applied migration was changed.

The proof compares both preview responses with their original function definitions inside one rolled-back transaction when no closures exist: behavior is identical. With a closure, both lists omit blocked times, the later-page cursor advances without duplicates, returned field names are unchanged, and no owner ID or private closure data is added. Calls through the existing service role succeed, while direct time-off table reads remain denied to anonymous, authenticated and service roles. A trusted postgres-only read policy supports the definer functions.

The prior prototype intentionally demonstrated that submission guards alone left misleading public slots; that gap is now closed **locally**, not live. Production source-baseline guards, ownership/ACL readback, lifecycle and UI gates below still apply.

## Lifecycle now proved locally
The guarded lifecycle candidate adds active/version state, immutable range/history guards, a private receipt table, an owner-only affected-booking preview and a closed JSON create/remove function. Preview responses include owner-visible attendee/timezone/times. A review fingerprint covers the owner, range, UTC boundaries and ordered booking IDs/versions/details; it is an optimistic-concurrency check, not an authentication token. UTC function settings make it stable across database session timezones.

Tests prove stale preview rejection, two same-operation saves producing one closure, changed-operation rejection, actor/closed-payload checks, cross-owner and stale-version remove denial, immutable ranges/history, concurrent removes producing one version change, receipt retries, reopening public slots and preservation of existing appointments. A separately connected booking observed holding the owner lock forces the waiting lifecycle save to request a fresh review.

A retried historical create returns its original receipt **without reactivating** a removed closure. The response includes `replayed`; the future UI must refresh current records and distinguish confirmation of an earlier operation from a new active closure. HTTP authentication/rate limits, browser-facing grants, actual controls and production migration/release work remain unimplemented.

## Production design and acceptance gates
1. Add a real owner-only table with immutable range/timezone boundaries, versioned activation/removal, explicit RLS/ACL and a reviewed owner/time-range index. A range timezone applies consistently across every current/future service; do not infer it silently from one rule.
2. Implement a closed authenticated API/RPC with expected actor, operation ID and version checks. Keep idempotent receipts and recoverable unknown-result retries. The closed JSON lifecycle is locally tested but still has no production API or browser-facing grants; add rate limits before enabling it. If authenticated users can execute the RPC directly, the rate limit must cover that path too; an HTTP-only limit is insufficient.
3. Owner preview must list/count affected existing appointments without canceling, moving or messaging them. Revalidate under the owner lock at save; require renewed review if the affected set changed. The lifecycle candidate now revalidates the preview fingerprint under the lock; the owner-facing review UX is still missing.
4. Carry the locally proven overlap predicate into both public slot-list paths and authoritative booking saves using a reviewed new migration. Preserve the owner-before-calendar lock order. Review any future reactivation/reschedule UPDATE path too; the prototype only guards INSERT because current saved appointment times are immutable.
5. Add clear owner controls for inclusive dates, business timezone, save/retry feedback, affected bookings and removing time off. Calendar working-hour patterns must distinguish time off without claiming verified free slots. Public responses must not expose private time-off labels, owner IDs or affected bookings.
6. Replace or optimize the deliberately exhaustive second-resolution day-boundary reference only after parity tests. Keep an explicit behavior for skipped civil dates and timezone rule updates; benchmark the final implementation before claiming production performance.
7. Before release: fresh recovery/restore rehearsal, immutable new migration, source-baseline guards, independent function/ACL/history readback, staging application tests and public/private concurrency tests. Never edit the already-applied PR31 migrations. Verify legacy behavior with no time-off rows.
8. Rollout/rollback must preserve already-created closures. Disabling creation is not permission to silently reopen saved time off. Do not remove guards/slot filtering while active closures exist.

## Shared request contract
`app/lib/workspaceTimeOff.ts` now defines preview/create/remove inputs for the future authenticated API and owner screen. It rejects unsupported/missing/inherited fields, malformed actor/record/operation identifiers, invalid civil dates, reversed or over-366-day ranges, invalid timezone names, malformed review fingerprints and invalid versions. Valid requests are copied without normalization so retry identity is preserved. `node scripts/test-time-off-contract.cjs` passed 77 checks without network/database calls.
This module is not imported by an API route or UI yet. Authentication, actor comparison, byte limits, rate limits, database authority and response validation remain separate required layers. JavaScript timezone validation does not replace PostgreSQL validation or skipped-civil-day detection. No production endpoint is enabled by this change.
Rate-limit implementation constraint: the existing public-booking throttle commits in a separate RPC specifically because a failed booking transaction would roll back its counters (20261121000000_public_booking.sql). For owner time off, do not simply increment a counter and then raise a validation/conflict exception in the same transaction. A directly executable authenticated RPC needs a non-bypassable durable quota strategy, such as committed admission permits with server-side consumption checks, or a structured non-throwing result protocol whose counter writes survive validation failure. A separately callable throttle alone does not enforce admission to another directly callable RPC. Preserve cookie-verified owner identity and never trust a body-provided owner in a service-role facade.

## Disabled authenticated API candidate
`app/api/workspace-time-off/route.ts` now implements POST preview/create/remove behind `WORKSPACE_TIME_OFF_ENABLED === 'true'` (unset/off by default; no environment changed). It verifies origin, content type, cookie-authenticated getUser, a streamed 6000-byte input limit, closed request fields and expected actor before invoking the proposed `workspace_time_off_request(payload)` RPC using the cookie client. It does not use service-role credentials. Raw database errors/fields are never forwarded.
The proposed RPC MUST be implemented before enabling: authenticated owner derived from auth.uid(), durable non-bypassable quotas, structured `{ok:false,code}` failures (`rate_limited`, `review_changed`, `conflict`, `invalid`), and `{ok:true,actorId,preview}` or `{ok:true,actorId,record,replayed}` success. Database quota enforcement is NOT implemented by this route. Existing prototype functions do not satisfy this production protocol. Response projection validates actor, bounded/unique affected records, review token, intervals, record ownership, request-matching create/remove receipts and historical replay flag. UI must reload current records after replay, as noted above.

These are not hosted integration or browser tests. No GET/list handler or owner UI is implemented yet. Do not turn on the gate or claim the feature shipped based on these tests.
