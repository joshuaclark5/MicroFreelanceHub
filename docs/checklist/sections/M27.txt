Execution and state

[ ] M27-011  Give every run a stable tenant-scoped event ID, rule version, source record ID and idempotency key. Record creation before work begins so a crash cannot lose the intended action.

[ ] M27-012  Use run states Queued, Running, Waiting, Awaiting approval, Succeeded, Failed and Cancelled. Distinguish a waiting timer from a failed action and a provider acceptance from confirmed delivery.

[ ] M27-013  Recheck source record state, access, consent and cancellation immediately before sending or changing a record. A stale queued snapshot must not send a reminder for an invoice paid since scheduling.

[ ] M27-014  Make event handling idempotent. Concurrent workers processing the same event and rule version must produce one intended task, message or record transition.

[ ] M27-015  Retry transient failures using bounded delays of 1 minute, 5 minutes, 15 minutes, 1 hour and 6 hours, honoring provider retry instructions. Permanent invalid-recipient or revoked-access failures require correction.

[ ] M27-016  Before retrying an ambiguous provider result, reconcile using the provider request or idempotency identifier. Do not resend solely because a response timed out.

[ ] M27-017  Support cancellation by run, source record and automation rule. Explain whether Disable stops only future events or also cancels queued work; offer both choices explicitly.

[ ] M27-018  Use the company IANA timezone for active hours. Offer weekdays Monday through Sunday and start/end time controls; move delayed sends to the next allowed window without duplicating them.

[ ] M27-019  Snapshot the published automation version for an active run. Editing a draft affects new runs only; old runs retain the original steps and data mappings.

[ ] M27-020  Keep approval requests scoped to the assigned owner or authorized role. Approval displays the exact recipient, body and record changes; Reject marks the waiting action cancelled.
