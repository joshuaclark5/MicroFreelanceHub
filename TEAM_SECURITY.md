# Team security boundary

Local source candidate, not a deployed service. The isolated team schema does not alter solo client/project/invoice/time/CRM permissions. Resource work must reference team workspace/membership keys separately.

- Owner/admin/member permissions are enforced in security-definer RPCs with fixed search paths, current auth.uid(), expectedActorId, and workspace-row locks. Authenticated users cannot write tables directly. team_role(uuid) supports scoped resource RLS. Exactly one owner is permitted; owner account deletion is restricted; normal removal/demotion cannot delete the owner. Creation requires a currently verified auth.users owner. Ownership moves only after an owner proposes to an existing nonowner and that currently verified recipient explicitly accepts (old owner becomes admin). Proposal alone changes no membership roles.
- Cookie-authenticated route verifies getUser, same-origin JSON mutations and closed bounded input. GET returns no token hashes or recipient bindings. Invitations and receipts have no direct authenticated SELECT grants.
- Invite secrets are 32 cryptographically random bytes, generated only in the server route. Only SHA256 reaches SQL. Acceptance sends the token in the POST body (not query); the route hashes/removes it. No application token logging, external send, email or fake delivery is implemented.
- An invitation binds an existing confirmed auth.users identity and normalized email. Unknown/unconfirmed/ambiguous lookup creates an inert invitation with the same response/list shape, avoiding explicit account-existence disclosure. Later confirmation does not activate an inert invite. Acceptance rechecks identity, current confirmed email, workspace, expiry, revocation, consumption and issuer authority. Existing memberships are not overwritten by invitations.
- Invitations expire after seven days. Acceptance and token consumption commit with the operation receipt, or roll back together. A consumed token cannot create membership again. Exact acceptance replay returns the original historical receipt only while the actor remains a member; it does not reapply its historical role. Reload GET for current role.
- Invite issuance is deliberately nonrecoverable: a token exists only in the successful route response. If response is lost or uncertain, reload the invite list, revoke the old invitation, create a new operation/invitation. Never blindly retry issuance or generate a replacement secret for a persisted receipt. Operation receipts contain only hash-based requests, not raw tokens.
- Transfer proposals expire after seven days; snapshots expose transfer {transferId,userId,expiresAt} or null. Each proposal has a fresh immutable SQL-generated UUID. Accept/cancel require that exact transferId and compare it with the live proposal under the workspace lock; an unseen delayed operation cannot consent to or cancel a replacement. The UI must pin the reviewed transferId at confirmation opening. Only the owner can cancel. A live proposal cannot be silently replaced. Recipient removal clears it; expiry, cancellation, wrong target/workspace, missing membership and unverified acceptance deny without changing the active owner. Acceptance changes both roles, clears the proposal and writes the receipt in one workspace-locked transaction. Failed updates or receipt insertion roll everything back.
- Operation replay is actor-scoped and rechecks current access. Transfer, acceptTransfer and cancelTransfer receipts are never replayed; reload GET after uncertain outcomes. A used acceptance operation cannot consume a later proposal. Remove replay rechecks both the removed role and any current target role: an owner demoted to admin cannot recover admin-removal receipts, or member-removal receipts after the target rejoins as admin. Revoke replay likewise rechecks invitation role. Both admin and member may leave themselves, never the owner. Self-removal immediately loses receipt access; after rejoining, a self-leave receipt is historical only and never deletes the new membership. Replay is denied if the actor is now owner. Member demotion loses non-self management-receipt access. Invitation acceptance replay remains a historical receipt only, not a current role grant.
- Admission limits match snapshots: 100 workspace memberships per user, 1000 selected-workspace members and 1000 active pending invitations per workspace. Create and invitation acceptance take the same per-user advisory transaction lock before workspace locking, serializing admission across operation IDs/workspaces. Join and invitation issuance check workspace counts under the workspace row lock. Replays do not add rows or consume capacity. Invitations shown are only pending (unrevoked, unaccepted, unexpired); revoke, expiry and acceptance free capacity, so reload/revoke/recreate remains usable at the bound. Historical invitations and receipts are retained but there is no history view, archive or pagination feature. Limit rejection is an actionable HTTP 409. Privileged out-of-contract overflow still fails explicitly rather than silently truncating. Workspace lists are live reads, not cross-workspace transactional historical snapshots.

## Verification and release limits
Run node scripts/test-workspace-team-api.cjs and node scripts/test-workspace-team-db.cjs. Results/hashes are written to ../evidence-team (or OUT_DIR). Database proof is a disposable file-backed PGlite with fictional auth schema, authenticated non-bypass RLS roles and actual migration SQL; close/reopen is exercised. Queued calls use one serialized embedded backend, NOT independent-backend contention proof. API proof executes actual transpiled handlers and Node crypto but mocks cookies/Supabase transport. Real Supabase JWT/PostgREST behavior, deployment grants/ownership, rate limiting, independent-backend contention and production backup/restore remain release gates. Parent integration owns optimized build and full app/browser verification. No providers, real accounts/customer records, emails, pricing, production migrations or publication were used.
